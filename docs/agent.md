# Агент, который реально чинит код

UNTIL умеет запускать внешнего исполнителя по протоколу `until-builder/v2`. В репозитории есть reference-реализация этого протокола на локальной модели:

```sh
node scripts/agent/run-agent-proof.mjs --label run-1 --model qwen3:14b --attempts 3
```

Это не демонстрация. Команда копирует **настоящий код этого репозитория**, кладёт в копию **настоящий падающий регрессионный тест**, поднимает **настоящее ядро** и даёт **настоящему агенту** задачу починить. На выходе — публикуемый след.

## Что происходит

```
копия репозитория            ← настоящий код, настоящие тесты
  ↓
красный тест                 ← добавлен заранее, падает до правки
  ↓
ядро UNTIL                   ← ставит задачу, даёт бюджет попыток и allowlist
  ↓
агент (qwen3:14b / Ollama)   ← читает, прогоняет проверку, правит, повторяет
  ↓
независимый verifier         ← запускает ту же проверку отдельной ролью
  ↓
release candidate            ← только если проверка зелёная
```

Ключевое: **агент не может принять свою работу**. Вердикт выносит другая роль, и она запускает ту же команду, что и агент, но не доверяет его словам.

## Протокол билдера

Процесс-исполнитель получает на stdin один JSON и возвращает на stdout один JSON.

**Вход:**

```json
{
  "goal":       { "title": "…", "outcome": "…" },
  "spec":       { "summary": "требование к изменению", "checks": [ … ] },
  "verification": [
    { "profile": "repoTest", "command": "node", "args": ["--test", "test/*.test.mjs"] }
  ],
  "workspace":  "/путь/к/рабочей/копии",
  "allowedPaths": ["src/executor/workspace.js"],
  "attempt":    1,
  "feedback":   { "failedCheck": "вывод упавшей проверки" }
}
```

`verification` — это команда, зарегистрированная оператором, а не придуманная моделью. Агент получает её, чтобы прогнать ту же проверку, которую потом запустит независимый verifier.

**Выход:**

```json
{
  "status": "done",
  "notes":  "read the file as bytes instead of text",
  "edits":  [{ "path": "src/executor/workspace.js", "content": "полный новый файл" }]
}
```

`edits` — полный новый файл, а не диффа. Ядро применяет их атомарно, проверяет allowlist и сравнивает рабочую копию со снимком: правка вне разрешённого пути отклоняется и откатывается.

## Инструменты агента

Агент внутри своего процесса работает с инструментами и сам себя проверяет:

| Инструмент | Что делает |
|---|---|
| `run_check()` | запускает зарегистрированную оператором проверку и возвращает её вывод |
| `list_files(path)` | листинг каталога |
| `grep(pattern)` | поиск текста по репозиторию |
| `read_file(path)` | читает файл из рабочей копии |
| `patch_file(path, old, new)` | заменяет один точный фрагмент файла |
| `write_file(path, content)` | перезаписывает файл **полным** содержимым |
| `finish(summary)` | завершение |

Ответ модели — один JSON-объект за ход. Формат принудительно задан схемой Ollama (`format`), а разбор терпим к вариантам вроде `file` вместо `path`.

### Почему инструментов именно столько

Это не дизайн ради удобства — это результат прогона.

- **Без `list_files`/`grep` агент слепой.** Первая версия харнесса умела только читать и писать по известному пути. На реальной задаче агент выдумывал имена файлов (`test/snapshot.test.mjs`, `test/restore.test.mjs` — ни одного из них не существует) и сжёг весь бюджет шагов. **Набор инструментов билдера — часть протокола, а не деталь реализации агента.**
- **`patch_file` вместо `write_file` — по скорости и точности.** Переписывание файла целиком на 8.7 КБ — это тысячи токенов вывода и минуты генерации на CPU. Точечная замена — сотни токенов. Совпадение ищется от строгого к прощающему: точное, затем по нормализованным пробелам, затем по строке; в ответе указывается, какое правило сработало.
- **Агенту нужен сбой, а не хроника.** Ядро отдаёт билдеру сводку упавших проверок (`summarizeFailures`), а не весь лог тестов: на этом репозитории 27 символов вместо 6 644. Сырой лог остаётся в доказательстве.

## Границы, которые агент не может пересечь

- **Право записи задаёт оператор.** `allowedPaths` в контракте; попытка записать вне него отклоняется дважды — самим агентом и ядром.
- **Команду выбирает оператор.** Агент получает готовый argv и не может его изменить.
- **Секреты не наследуются.** Дочернему процессу передаётся только `PATH` (и `SystemRoot` на Windows).
- **Откат всегда возможен.** Снимок рабочей копии снимается до первой попытки; при исчерпании бюджета копия восстанавливается, а неудачная правка не может стать релизом.
- **Внешний процесс запускается только при `sandboxConfirmed: true`** и в отдельном окружении: исполнитель — обычный процесс с правами пользователя.

## Что этот прогон доказывает и чего не доказывает

**Доказывает:** цикл «правка → проверка → обратная связь → новая попытка» работает на реальном коде с реальной моделью; границы удерживаются; неудачная попытка не превращается в релиз.

**Не доказывает:** качество какой-либо модели как таковой. Локальная 14B-модель — это нижняя граница. Если конкретная модель не справилась с задачей, это факт о модели, а не о контуре.

Прогон публикуется как `app/public/fixtures/agent-run.json` — с полным следом по попыткам, выводом проверки, вердиктом и состоянием аудита.

## Что показали прогоны

| Прогон | Что изменилось | Что открылось |
|---|---|---|
| 1 | агент без инструментов поиска | выдумывает имена файлов, бюджет кончается |
| 2 | добавлены `list_files` + `grep` | файлы находит, но бюджет уходит на чтение |
| 3 | обратная связь сжата до сбоя (`summarizeFailures`) | доходит до `patch_file`, но не успевает сойтись |
| 4 | + `patch_file` с терпимым поиском фрагмента | правки применяются, проверка не сходится |
| 5–8 | 20 шагов, полная копия репозитория | **`patch_file` не вызывается ни разу: `grep → read_file → grep → …` до конца бюджета** |

Итог: инструменты и обратная связь работают — агент перестал гадать. Дальше упирается **решение модели довести дело до правки**. На локальной `qwen3:14b` на CPU это не выходит. Для боя нужен агент с сильной дисциплиной использования инструментов (hosted-модель, Claude Code, OpenHands) — через тот же протокол и тот же allowlist.

Побочный эффект прогонов оказался ценнее самой задачи: **одиннадцать дефектов на стыке «модель ↔ ядро», которых не видно ни в чтении кода, ни в юнит-тестах.** Подробности — в `docs/audit/technical-audit.md`, раздел 4.

## Какие модели есть на машине

Агент работает через Ollama `/api/chat` с принудительной JSON-схемой. Поэтому подходит любая instruct-модель: встроенный формат Ollama — это грамматика llama.cpp, а не API производителя. GGUF из LM Studio подключается без конвертации:

```sh
printf 'FROM F:\\LMStudioModels\\<папка>\\<модель>.gguf\n\nPARAMETER num_ctx 32768\n' > Modelfile
ollama create <имя> -f Modelfile
```

Железо этой машины: RTX 5070 (12 ГБ VRAM), 32 ГБ RAM, Ollama 0.40.16. Отклик — один ход агента, измерено смоук-тестом (`npm run agent:smoke`), тем же промптом и той же схемой, что и настоящий агент:

| модель | источник | вес | смоук | один ход |
|---|---|---|---|---|
| `qwen3:8b` | Ollama | 4.87 ГБ | PASS | 29.6 с |
| `qwen3:14b` | Ollama | 8.64 ГБ | PASS | — |
| `qwen3-vl:8b-instruct-q4_K_M` | Ollama | 5.77 ГБ | PASS | 46.2 с |
| `gemma3-12b:latest` | GGUF `gemma-3-12B-it-QAT-Q4_0` | 6.41 ГБ | PASS | 70.7 с |
| `qwen35-9b-uncensored` | GGUF `Qwen3.5-9B-Ultra-Uncensored-Heretic-Q4_K_S` | 4.98 ГБ | PASS | 31.9 с |
| `gemma3-27b-qat` | GGUF `gemma-3-27B-it-QAT-Q4_0` | 14.5 ГБ | PASS | 110.4 с |
| `bge-m3` | Ollama | 1.08 ГБ | — | эмбеддинги, не чат-модель |

Смоук отвечает на один вопрос: «верни один JSON-объект инструмента». Модель, которая на это не способна, не пройдёт полный прогон никакой длины.

Полный прогон по нескольким моделям подряд — `npm run agent:sweep -- --models a,b,c`. Каждый прогон пишет свой след в `.until/agent-runs/<метка>/report.json`, сводка — в `sweep-<метка>.json` и `.md`.

## Два дефекта, которые нашлись только на этих прогонах

Первый прогон по трём моделям вскрыл то, чего не видно на одной: **две из трёх не доходили до билдера вообще.**

| модель | что произошло |
|---|---|
| `qwen35-9b-uncensored` | контракт отвергнут: `$.tasks is not an allowed property; $.evidence_refs is not an allowed property` |
| `gemma3-12b:latest` | контракт отвергнут: `$.title is required; $.role is not an allowed property` |
| `qwen3:14b` | контракт принят, билдер отработал, правок ноль |

Оба падения — на шаге «owner пишет контракт», до билдера. Причина оказалась не в моделях, а в ядре:

**D25. Отклонённый ответ не возвращался модели.** Ядро брало ответ, проверяло его по схеме и отбрасывало. Модель, получившая тот же вопрос второй раз, повторяла ту же ошибку — а бюджет попыток на это не тратился впустую, он просто не доходил до повторного вызова.

**D26. Отложенный ретрай терялся.** Повтор задачи планировался на 100 мс вперёд. Внутренний цикл ядра брал задачу, не нашёл — и выходил: «работать нечем». Повтор, ради которого оператор и выдавал бюджет, не выполнялся никогда.

Обе правки — в ядре, не в моделях:

- `src/agents.js`: отклонённый ответ возвращается модели на следующей попытке вместе с текстом ошибки — попытка становится коррекцией, а не повтором;
- `src/store.js` + `src/kernel.js`: если задача запланирована на будущее, воркер ждёт её, а не закрывает прогон.

После правок тот же прогон на `qwen3:14b` идёт полным циклом, а на двух других моделях доходит до билдера.

## Что показал прогон по моделям

Каждый прогон — копия репозитория, засеянный дефект, настоящий падающий тест, настоящее ядро. Ничего не имитируется.

| прогон | модель | контракт | билдер | вердикт | релиз | аудит | время |
|---|---|---|---|---|---|---|---|
| r9 | `qwen3:14b` | 1 попытка | 3 попытки, правок 0 | отказ | нет | valid | 18.3 мин |
| r10 | `qwen35-9b-uncensored` | 3 → 2 → 2 попытки | 3 попытки, правок 0 | отказ ×3 | нет | valid | 17.9 мин |
| r10 | `gemma3-27b-qat` | 2 → 1 попытки | 3 попытки, правок 0 | отказ ×3 | нет | valid | 23.6 мин |
| r11 | `gemma3-12b:latest` | 3 (исчерпаны) → 2 → 2 попытки | 3 попытки, правок 0 | отказ ×3 | нет | valid | 30.6 мин |
| r11 | `qwen3:14b` | 1 попытка в каждом поколении | 3 попытки, правок 0 | отказ ×3 | нет | valid | 14.1 мин |

Что видно в цифрах r10:

- **контракт** перестал быть узким местом: модели отвергали по 1–2 раза, получали текст ошибки и отвечали корректно — 3 попытки в первом поколении, 2 в следующих;
- **цикл переработки** отработал полностью: 4 генерации, 12 завершённых задач, 4 провала, цель честно остановилась как `blocked_rework` вместо бесконечного цикла;
- **билдер** трижды прогнал проверку и ни разу не вызвал `patch_file` — правок ноль;
- **откат** сработал побайтово (`workspaceRestored: true`), релиз не выпущен, цепочка аудита цела (75 событий, `auditValid: true`).

Итог по моделям честный: **контур работает, модель — нет.** Ни одна из локальных моделей не дошла до правки. Это факт о моделях, а не о протоколе: тот же протокол, тот же allowlist, та же независимая приёмка.

```sh
npm ci --ignore-scripts

```

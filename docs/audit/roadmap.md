# Роадмап пересборки UNTIL: от ядра к продукту (0.3 → 1.0)

Дата: 14 ноября 2026. Входные данные: `technical-audit.md`, `market-landscape.md`, `positioning.md`, `go-to-market-hh.md`.

Документ отвечает на вопрос «что именно доделать, дожать и усилить в разы». Он не пересказывает аудит — он раскладывает его по итерациям с проверяемым результатом на каждой.

---

## 0. Куда мы идём

**Было (0.2):** открытое ядро автономного продуктового цикла. Библиотека + CLI + манифест-сайт.
**Стало (1.0):** продукт, который в контуре клиента доводит разрешённую задачу до принятого релиза, доказывает это его собственным тестом и оставляет полный аудит-след.

Единственная метрика успеха продукта: **число принятых релизов, произведённых без участия человека в цикле, на единицу затраченного времени и денег.** Всё остальное — активность, а не ценность.

Три измерения, по которым 1.0 отличается от 0.3:

| Измерение | 0.2 / 0.3 | 1.0 |
|---|---|---|
| Что делает система | Создаёт артефакты; с 0.3 — меняет код по циклу «упало → починил» | Меняет код в чужих репозиториях, готовит PR, катит по allowlist'у |
| Откуда берётся работа | Человек вносит сигнал из файла | Коннекторы: issues, тикеты, аналитика, инциденты |
| Чем это доказывается | Собственный тест проекта | Тот же тест + подписанный выпуск + SBOM + attestation + ИБ-ревью |
| Кто может пользоваться | Инженер, готовый читать JSON и писать DSL | CTO, который поднял локально и принёс в ИБ |

## 2. Итерация 0.4 — «Одна настоящая задача» (2–3 недели)

**Цель итерации:** одно публичное доказательство, которое нельзя принять за демонстрацию.

Это самая важная итерация. Всё остальное — упаковка. Пока нет одного реального прогона на чужом репозитории, любые разговоры с покупателями идут в долг.

### 2.1 Подключить настоящего coding-агента

Выбрать одного и подключить через протокол v2 (исполнитель возвращает правки):

| Кандидат | Плюсы | Минусы |
|---|---|---|
| **Claude Code** | Сильнейшее качество правок, удобный CLI, умеет читать репозиторий | Нужна подписка/ключ; проприетарный |
| **OpenHands** | Открытый, запускается локально в Docker, есть свой sandbox | Дороже по настройке, качество ниже Claude Code |
| **Cursor CLI / Aider** | Просты, работают с локальными моделями | Cursor — закрытый; Aider слабее на сложных задачах |

**Рекомендация:** начать с Claude Code (быстрый и качественный результат ради первого прогона), параллельно поддержать OpenHands (открытый путь для аудитории «мы не хотим платить Anthropic»).

### 2.2 Выбрать задачу, которая честно воспроизводима

Критерии отбора:

- задача из **публичного репозитория** с MIT-лицензией (юридически чисто для публикации);
- в репозитории **уже есть тест**, который падает из-за описанного дефекта;
- дефект **неочевиден**, чтобы доказать, что агент не угадал;
- изменение **затрагивает 1–3 файла** (иначе цикл становится дорогим);
- задача **не из бенчмарков SWE-bench** — нужен честный, не тренировочный пример.

Хорошие кандидаты: мелкие реальные баги в популярных OSS-проектах с воспроизводимым репро.

### 2.3 Опубликовать прогон целиком

Не скриншот. Полный пакет:

```
docs/proof/v0.4-real-repo/
  task.json            # исходная задача: issue, воспроизведение, ожидаемое поведение
  contract.json        # контракт, который получила роль
  attempts.jsonl       # каждая попытка: вывод упавшего теста, предложенная правка
  diff.patch           # итоговый diff
  test-before.txt      # вывод теста ДО
  test-after.txt       # вывод теста ПОСЛЕ
  events.jsonl         # hash-chain журнал
  release/             # подписанный кандидат
  verify.sh            # одна команда, которая повторяет всё
```

**Критерий готовности:** независимый человек запускает `verify.sh` на чистой машине и получает тот же результат.

### 2.4 Переделать «repository-cycle» в proof-сценарии

`scripts/proof.mjs` сейчас содержит сценарный builder с заранее записанным ответом. Сценарий должен:

- использовать **тот же repair-цикл**, что и в бою (без отдельной ветки кода);
- явно маркировать `mode: "deterministic_builder_not_model_intelligence"`;
- **не выдавать** детерминированный прогон за доказательство интеллекта.

### 2.5 Связать Evolver с реальным приоритетом

Либо приоритет в `Director` начинает считаться по геному (тогда эволюция влияет на поведение), либо Evolver уходит из публичного продукта в лабораторный раздел. Сейчас он доказывает то, чего в продукте нет — это хуже, чем отсутствие.

## 3. Итерация 0.5 — «Вход: коннекторы» (3–4 недели)

**Цель:** работа приходит сама, без ручного внесения сигналов.

### 3.1 Коннектор чтения (обязательный минимум — два)

| Коннектор | Что даёт | Почему первый |
|---|---|---|
| **GitHub Issues** | Реальные, живые задачи от пользователей; естественный источник «наблюдения» | Самый сильный сигнал: это настоящий баг, который кто-то потратил время, чтобы описать |
| **Аналитика / Sentry** | Метрики, на которых измеряется outcome | Нужен для замыкания цикла «релиз → наблюдение → следующая работа» |

Остальные — по мере надобности: Linear/Jira, Discord/Slack, поддержка (Intercom/Zendesk), Stripe.

### 3.2 Контракт коннектора

Коннектор — не «ещё один модуль». Он обязан:

- приводить внешние данные к **типизированному сигналу** с `kind`, `source`, `observed_at`, `consent`;
- **не уметь** создавать release и **не выдавать** права — только читать и добавлять сигналы;
- работать **в dry-run по умолчанию**: сначала показывает, что он принесёт, потом пишет;
- идемпотентен: повторный опрос не создаёт дублей (по внешнему ID);
- **логировать** в hash-chain, что и откуда пришло.

### 3.3 Коннектор записи (после 0.5)

PR-ы и issue-комментарии. Это уже требует прав, поэтому 0.5 — только чтение.

## 4. Итерация 0.6 — «Выпуск: подпись и доказуемость» (3–4 недели)

**Цель:** продукт, который ИБ-ревьюер может одобрить.

Рыночное исследование прямо показывает: у российского покупателя главный страх — **ответственность**, и вето принадлежит security-ревьюеру. Пока это не сделано, продукт не продаётся в компании с 10+ разработчиками.

### 4.1 Подпись и provenance

- **Sigstore / cosign** — подпись каждого release candidate (бесплатно, ключи не нужны).
- **in-toto attestation** — что именно было произведено, из какого коммита, какими проверками.
- **SLSA provenance** — уровень, который заявляем честно (не выше, чем можем подтвердить).
- **SBOM на каждый выпуск**, а не только в CI.

### 4.2 Документы, которые читает ИБ

| Документ | Для кого | Объём |
|---|---|---|
| `SECURITY.md` (расширенный) | ИБ | Модель угроз, что доверяем, что нет, что вне контура |
| Data-flow / 152-ФЗ документ | ИБ + юрист | Что покидает контур, что нет, где хранится, сроки хранения |
| Маппинг ISO 27001 / 42001 | ИБ | Какой контроль закрыт, какой в работе |
| `PRIVACY.md` | Юрист | Что собираем, зачем, как удалить |
| `security.txt` | Автоматические сканеры | Стандартный маршрут для отчётов об уязвимостях |

### 4.3 Ужесточение границ

- **Граница prompt injection**: разметка недоверенного содержимого, карантин инструментов, проверка инструкций в данных.
- **Ограничение размера входа** модели: бюджет на промпт, а не только на вызовы.
- **Per-goal бюджет и burn-rate**: сколько денег цель может потратить и с какой скоростью.
- **Per-goal стоимость принятого релиза** — главная метрика в `economics()`.

## 5. Итерация 0.7 — «Продукт, а не библиотека» (4–6 недель)

**Цель:** то, что можно включить в ИТ-контур компании.

1. **HTTP API** поверх ядра: `POST /goals`, `POST /signals`, `GET /goals/:id`, `POST /goals/:id/run`, `POST /goals/:id/replay`, `GET /audit`. Тот же детерминированный слой, HTTP — только транспорт.
2. **Веб-панель**: текущий статус, очередь, артефакты, вердикты, выпуски, аудит, стоимость. Сейчас `app/` — статический проигрыватель; он должен стать интерфейсом к живой системе.
3. **Мультиярендность и роли**: workspace, пользователи, роли (owner / builder / verifier / reader), аудит действий.
4. **Наблюдаемость**: OpenTelemetry-трейсы задач, метрики (время цикла, доля отклонений, стоимость релиза), дашборд.
5. **Планировщик**: запуск по расписанию и по событию (новый issue → новая задача), а не только polling-цикл.
6. **Slack/Telegram-уведомления**: «релиз принят», «нужна твоя проверка», «цель заблокирована».

## 6. Итерация 1.0 — «Готовность к продаже» (4–6 недель)

**Цель:** можно продавать, можно внедрять, можно выдержать ИБ-ревью.

1. **Публичный бенчмарк на N задачах** (рекомендуется 30–100) с зафиксированным протоколом, золотым набором и опубликованными сырыми трассами. Формат: `accepted / attempted`, стоимость, время, число попыток. Без этого все разговоры о «мы заменяем команду» останутся маркетингом.
2. **Парные пилоты**: 3 компании, одинаковые задачи, человек против системы, полная телеметрия. Публикуется даже если результат невыгодный — иначе это не доказательство.
3. **Модель цены**: базовый тариф за рабочее пространство + тариф за принятый релиз с потолком. Никогда за места и не за токены. (Рекомендация исследования: ≈59 000 ₽/мес за пространство, ≈15 000 ₽ за принятый релиз с потолком.)
4. **Коммерческая лицензия** (Enterprise) поверх MIT-ядра: SSO, журналирование, централизованная политика, SLA.
5. **Онбординг за 15 минут**: `until init --from-repo` → подключить коннектор → первый прогон. Сейчас путь к первой ценности требует ручной настройки DSL.

## 7. Технические решения, которые нужно принять сейчас

| Вопрос | Варианты | Рекомендация | Почему |
|---|---|---|---|
| Git-интеграция | Своя реализация поверх `git` CLI / libgit2 / обёртка над хостингом | **Обертка над `git` CLI в изолированном окружении** | Ноль зависимостей, тот же аргумент, что и у ядра. Своя реализация git — это месяцы и новый класс багов |
| Хранилище состояния | SQLite (сейчас) / Postgres / файловое | **Оставить SQLite, добавить слой репозитория** | Ноль зависимостей + локальность — главный актив. Миграция на Postgres — вопрос 1.0+, не раньше |
| Планировщик | polling / cron / event-driven | **Event-driven + cron** | Polling с `sleep(1000)` не масштабируется и сжигает ресурсы |
| Доступ к моделям | Только OpenAI-совместимый / добавить провайдеров | **Оставить OpenAI-совместимый + добавить Anthropic Messages API** | Часть аудитории не может использовать Ollama, но может Anthropic. Один дополнительный адаптер — дёшево |
| Очередь | Внутренняя на SQLite / Temporal / BullMQ | **Оставить внутреннюю** | Внешняя очередь разрушает главное свойство — «скачал и запустил» |
| Мультиярендность | Workspace-файлы / Postgres | **Workspace-файлы для 1.0** | Минимально достаточная мультиарендность = отдельный каталог на клиента |
| Исполнитель | Один агент / роутер по сложности | **Роутер: дешёвая локальная модель на классификацию, дорогая на правки** | Прямо влияет на главную метрику — стоимость принятого релиза |

## 8. Чего делать нельзя

1. **Не расширять ядро новыми ролями.** Ролей шесть, они покрывают цикл. Новые роли = новые места для обхода границ.
2. **Не добавлять зависимости без крайней необходимости.** Ноль runtime-зависимостей — главный аргумент для ИБ и главная причина, по которой продукт выглядит «серьёзно» за 2 100 строк.
3. **Не добавлять фичи, пока нет ни одного платящего клиента.** Онбординг, коннекторы, подпись, бенчмарк — важнее любой новой роли.
4. **Не обещать «замену команды».** Недоказуемо, невозможно ценообразовать, уязвимо. Продавать принятый релиз.
5. **Не переписывать ядро.** Оно проверено 82 тестами и является активом. Пересборка — это надстройка, а не ревизия.
6. **Не запускать массовую рассылку вакансий по hh.ru** — это нарушение правил площадки и закона о рекламе (детали в `go-to-market-hh.md`).

## 9. Порядок и ресурсы

```
0.4  Одна настоящая задача          ← без этого остальное не имеет смысла
 0.5  Коннекторы чтения              ← работа приходит сама
 0.6  Подпись и документы ИБ         ← вето снимается
 0.7  API, панель, наблюдаемость     ← это становится продуктом
 1.0  Бенчмарк, пилоты, цена, SLA    ← это можно продать
```

Каждая итерация заканчивается одним проверяемым артефактом, который публикуется:

| Итерация | Публикуемый артефакт |
|---|---|
| 0.4 | Один реальный прогон + `verify.sh` |
| 0.5 | Два коннектора + документация по контракту коннектора |
| 0.6 | Подписанный выпуск + SBOM + data-flow документ |
| 0.7 | Живая панель вместо проигрывателя |
| 1.0 | Бенчмарк на N задачах + результаты трёх пилотов |

**Оценка:** 0.4 — 2–3 недели, 0.5 — 3–4, 0.6 — 3–4, 0.7 — 4–6, 1.0 — 4–6. Итого ≈ 4–5 месяцев соло-разработки. Это реалистично, если не распыляться.

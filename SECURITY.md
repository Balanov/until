# Security policy

## Workspace mutation boundary

The executor may change files in the workspace, so the boundary is explicit:

- every edited path is normalized and resolved inside the workspace root; traversal, absolute paths and drive letters are rejected;
- excluded directories (`.git`, `.until`, `node_modules`, `venv`, `dist`, `build`, `target`, `vendor`, …) are never entered;
- `goal.policy.build.allowedPaths` restricts the builder to an explicit set of files or directories. A change outside that set is rejected, rolled back and recorded as `out_of_scope_edit`;
- a change is applied atomically and is content-hashed, so the exact bytes are known;
- if the attempt budget is exhausted, the workspace is restored **byte for byte** from a snapshot taken before the first attempt. A failed attempt cannot leave a half-changed repository;
- excluded and allowed paths are evaluated lexically and against the real path, so a symlink cannot be used to escape the workspace.

`sandboxConfirmed: true` remains an administrator assertion. These checks constrain *which paths* a process may write; they do not contain the process itself. A builder still runs with the operating-system user's permissions and must be executed in a disposable sandbox.

## Builder protocols

Two protocols are supported. In both, the builder is an operator-registered argv profile — the model never chooses the executable, its arguments or its environment.

- `until-builder/v1`: the harness edits the workspace itself and returns a summary. The engine detects the resulting diff and verifies it.
- `until-builder/v2`: the harness returns `{ edits: [{ path, content }] }`. The engine applies the edits itself, enforces the allowlist and owns the rollback.

Either way the harness receives the failing check output as feedback on the next attempt. Check output is truncated before it is returned, and it is treated as untrusted data.

## Command profiles

Acceptance command profiles are registered by the operator, never generated by a model. They use argv arrays without shell interpolation, bounded output, timeouts, an environment allowlist and realpath checks for artifacts and working directories. Exit code 0 alone is insufficient: a profile must produce the declared output expectation (`contains`, `jsonField` or `exitCode`).

On Windows a profile whose command ends in `.cmd` or `.bat` cannot be executed directly without a shell. Such profiles are routed through `cmd.exe /d /s /c` **only** when the full command line matches a conservative character allowlist (`A-Z a-z 0-9 _ - . / = : @ , + ~` and spaces). Any other character, including shell metacharacters, causes the profile to be rejected before execution. Register `npm.cmd` on Windows rather than `npm`.

## Reporting a vulnerability

Report vulnerabilities privately through [GitHub Security Advisories](https://github.com/Balanov/until/security/advisories/new). Include the affected version, a minimal reproduction, impact and a safe contact channel. Do not include real credentials, customer data or exploit payloads against third-party systems.

## Trust boundaries

UNTIL treats model output, external documents, repository content, skills, tool results, remote cards and connector payloads as **untrusted data**. Role text is not authorization. The deterministic kernel owns tasks, capabilities, budgets, verdicts and side effects.

- Unknown task kinds, check types and outbox actions fail closed.
- Builders cannot verify their own artifacts or publish them.
- Only a different verifier role can create a verdict.
- Release requires both an independent passing verdict and the evidence gate.
- Synthetic or inferred signals cannot unlock delivery.
- High-risk contracts stop with `blocked_risk` unless a separate risk boundary is implemented.
- Stop uses a persistent epoch; late results are rejected before dependent work or release.
- External actions use stable idempotency keys and a durable outbox.

## Execution warning

**UNTIL is not an OS sandbox.** The built-in artifact executor is intentionally narrow, but an external builder or command profile is a process with the operating-system user's permissions. File checks constrain artifact paths and real symlinks, but they do not contain a malicious process.

Run external builders only in a disposable OS, VM or container sandbox with:

- no inherited secrets;
- a dedicated low-privilege identity;
- read-only base inputs and a separate writable output volume;
- explicit network egress rules;
- CPU, memory, process, output and wall-time limits;
- tracked process trees and a tested kill switch.

`sandboxConfirmed: true` is an explicit administrator assertion, not a sandbox implementation. Do not set it for an unisolated process.

## Secrets and data

API keys are read only from environment variables named in configuration. Do not put keys in `until.config.json`, goals, signals, artifacts, issues or proof bundles. Review all traces before sharing them: source content can contain personal data, proprietary code or credentials even without an explicit secret field.

SQLite and JSON proof files are not encrypted. Apply OS disk permissions, retention and backup policies appropriate to the source data. Use real-participant consent and purpose limitation for customer research.

## External effects

Local release candidates are not production deployments. Idempotency prevents known duplicates inside UNTIL, but cannot undo an external effect or guarantee exactly-once behavior at a provider without provider-side deduplication or reconciliation. A provider receipt is an assertion, not independent physical evidence.

Production deployment, payments, bulk outreach, IAM, destructive operations and irreversible changes require a separately reviewed risk boundary and, where applicable, legally required human authorization.

## Supported version

Security fixes are applied to the current `main` branch and the latest tagged release. Version 0.2 is an engineering MVP; perform your own threat model and paired validation before operational reliance. Version 0.3 adds workspace mutation with an allowlist and a byte-for-byte restore, so re-run that validation against the executor specifically.

## Supply chain

The core has **zero runtime npm dependencies**, which is the largest single supply-chain control in this project. CI enforces it: `npm audit` runs for runtime and site dependencies, CodeQL runs `security-and-quality` queries, a CycloneDX SBOM is published as a build artifact, and `dependency-review` blocks moderate-or-worse advisories in pull requests. The website build has its own dependency tree and is audited separately.
